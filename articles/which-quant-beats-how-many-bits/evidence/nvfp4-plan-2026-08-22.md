# NVFP4 rungs: registered plan, 2026-08-22

Written before any NVFP4 run started, to the same rule as
`moe-ladder-plan-2026-08-16.md`: the design and its known weaknesses are on
record before the numbers exist.

## What is being measured

NVFP4 is Blackwell's four-bit floating-point format. The RTX 5080 has native
tensor-core support for it, and this llama.cpp build is compiled `sm_120a` with
NVFP4 quantize and dequantize paths in `libggml-base` and 56 NVFP4 symbols in
the CUDA backend. A load probe served
`WhiskyAKM/LFM2.5-2.6B-NVFP4-GGUF/lfm2.5-2.6b-nvfp4.gguf` at 2,028 MiB against
2,104 MiB for that model's UD-Q4_K_XL, so the format works here and is
comparably sized.

The question is whether a four-bit float beats a four-bit integer quantization
of the same model on accuracy, speed, or both.

## The confound, stated first

**No official publisher ships an NVFP4 GGUF at all**, so there is no way to
measure officially-built NVFP4 under llama.cpp. Verified against the repo file
listings on 2026-08-22 rather than assumed:

| repo | .gguf | .safetensors |
|---|---:|---:|
| nvidia/Gemma-4-26B-A4B-NVFP4 | 0 | 4 |
| nvidia/Qwen3.6-35B-A3B-NVFP4 | 0 | — |
| nvidia/Gemma-4-31B-IT-NVFP4 | 0 | 4 |
| RedHatAI/gemma-4-26B-A4B-it-NVFP4 | 0 | 1 |
| RedHatAI/Qwen3.6-35B-A3B-NVFP4 | 0 | 3 |
| unsloth/gemma-4-12b-it-NVFP4 | 0 | 1 |
| unsloth/Qwen3.6-35B-A3B-NVFP4-Fast | 0 | 5 |

Converting one is not a way around it. `convert_hf_to_gguf.py` in this tree has
no NVFP4 support at all, and its `--outtype` choices are f32, f16, bf16, q8_0,
tq1_0, tq2_0 and auto. Converting an official NVFP4 checkpoint dequantizes it to
16-bit, so the result would carry an NVFP4 label while measuring BF16. Serving
the official weights as they are needs vLLM or TensorRT-LLM, neither of which is
installed here and either of which would replace the engine every other run in
this campaign used.

So every NVFP4 target below is a third-party GGUF conversion, because that is
the only NVFP4 llama.cpp can load. That is not a shortcut taken here; it is the
position any llama.cpp user on Blackwell is in, and it is worth reporting as
such.

So an NVFP4 rung differs from its Q4 sibling in **two** ways at once: the
number format, and who produced the file. The existing ladder is unsloth UD
builds with a documented imatrix method; these are not. That is the same defect
the article already records for LFM2.5, and it caps what these runs can support:

- They can answer "what does the NVFP4 build available to me cost against the
  Q4 build available to me", which is the question someone choosing a file
  actually faces.
- They cannot answer "is NVFP4 better than Q4_K_XL as a format", because no
  matched-publisher pair exists to ask it with.

Any result from these rungs is reported with that limitation attached, and a
separation is not evidence about the format on its own.

**LFM2.5-8B-A1B has no NVFP4 GGUF anywhere**, from any publisher, so its ladder
has no NVFP4 rung. Recorded rather than substituted.

Selection rules, applied before looking at any score:

- Reject derivative tunes: `uncensored`, `heretic`, `abliterated`, `Distill`.
  A different model is not a width comparison.
- Reject partial quantizations: `Experts-Only`, `MoE-MLP`. Those leave some
  tensors unquantized and cannot answer what NVFP4 costs.
- Reject files carrying a second quant in the name (`-Q8_0`, `-Q4_K_M`,
  `-BF16`) where a plain NVFP4 file exists in the same family.
- Prefer the instruction-tuned build matching the existing ladder, and take the
  QAT variant as its own rung rather than as a substitute.

At 13.45 GiB the 26B-A4B NVFP4 file is the only one of that model's rungs
expected to sit on the card without expert offload; its UD-Q4_K_XL is 16,222
MiB and needs `-ncmoe 8`. Qwen at 18.36 GiB will need offload as its other rungs
do. Both are throughput observations, not accuracy ones.

## Harness change this required

`-hf <repo>[:quant]` matches the text after the colon against known quant names.
These repos name files `gemma-4-E2B-it-NVFP4.gguf`, which matches nothing, so
`-hf repo:file.gguf` fails with "no GGUF files found in repository" while
printing the file it just refused. `run_arm.sh` and `tune_ncmoe.sh` now split a
target written `repo#file` and pass `-hf repo -hff file`. Existing arms, which
carry no `#`, are unaffected.

## What would make this conclusive

A matched-publisher pair: one publisher shipping both an NVFP4 and a UD-Q4 build
of the same model from the same base weights and imatrix. If unsloth or LiquidAI
publish NVFP4 later, those rungs replace these and the comparison becomes a
format comparison rather than a file comparison.
